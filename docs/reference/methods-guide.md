## P0：先确定适用范围，再选择实现

本方案以本地**文本生成 LLM 及其运行系统**为主体，可扩展工具、Agent 和多模态输入。独立 embedding、reranker、语音合成、图像/视频生成需要另外设计指标，本表不是所有 AI 模型的完整标准。

“普遍”指不同设备与模型能回答相同的评测问题，使用可对照的定义和证据；不要求同一命令、同一底层事件或同一传感器。分析项表每行已有“基础 / 条件 / 核验”及具体前提。

| 边界                                      | 处理方法                                                                      | 无法满足时                                                                                   |
| ----------------------------------------- | ----------------------------------------------------------------------------- | -------------------------------------------------------------------------------------------- |
| CPU、独立 GPU、统一内存、NPU 及不同操作系统 | 先探测实际可用的后端、资源读数与权限；按设备层、进程层、引擎层记录            | 保留可得指标；缺失的测量标不可测，不根据其他平台数值补齐。                                   |
| 自回归、混合或其他生成架构                | 先确认是否存在可比的 prefill、decode、KV 状态；滑动窗口和预分配可能改变增长规律 | 不存在的架构指标标不适用，改报端到端耗时、整体资源、任务质量。                               |
| 接口型服务与封装桌面应用                  | 优先 API/CLI；桌面应用可录屏或人工计时，并记录起止事件与分辨率                 | 可测用户操作到显示的总时间；不能据此反推引擎阶段耗时，不与 API 计时直接混排。                  |
| 概率评分与生成答案评分                    | 先检查题目需 loglikelihood 还是 generate_until，适配对应接口                     | 仅能生成文本时可做独立命名的生成式评测；不能冒称完成原概率评分协议。                         |
| 语言与模态                                | 测前冻结用户需求、声明功能及必测能力；支持的输入仍需验证质量                  | 范围外是不适用；范围内缺能力是不支持，按协议判不合格或失分，保留原因。                       |
| 优化对照与参考基线                        | 同设备、同基座、同任务做受控对照；单个因素之外的变化写入差异清单              | 无有效基线时只发绝对结果；在其他设备测的高精度质量仅作注明混杂的参考，不用于目标设备加速比。 |
| 人工评审、代码执行与测量仪器              | 先估计每题评审时间、执行资源、仪器精度；容器、虚拟机或原生隔离环境按平台选择  | 缺标注/仪器/隔离环境则未测或不可测，不能把工具名称当作已经可执行。                           |
| 版本与设备组合数量                        | 先冻结有代表性的设备、后端和配置矩阵；边界附近再细测，正式验收与调参分开      | 不要求穷举全部组合；所有未覆盖单元公开标未测，保留筛选与停止规则。                           |

lm-eval 的[模型接口说明](https://github.com/EleutherAI/lm-evaluation-harness/blob/main/docs/model_guide.md)明确区分生成和对数似然请求。资源接口只对其管理范围负责：例如[MLX 峰值内存](https://ml-explore.github.io/mlx/build/html/python/_autosummary/mlx.core.get_peak_memory.html)不是整机全部内存，不能与其他统计值直接累加。

通用实施顺序是：身份/环境采集 → 加载与最小请求 → 计时和评分器预跑 → 适用项目正式测量 → 边界/持续负载及复核。这是降低无效实验成本的门槛流程，不改变关联度排名，也不要求每次重复已有且仍适用的审计。

## P1：实验配置与预跑

每次正式测试前建立一个不可覆盖的配置快照：

| 字段组   | 必填内容                                                         |
| -------- | ---------------------------------------------------------------- |
| 被测对象 | 硬件实例、模型 revision 及文件哈希、量化、引擎/驱动版本、生效参数  |
| 负载     | 题库版本、题目 ID、输入长度、输出预算、并发或到达率、是否自然结束 |
| 控制条件 | 缓存、预热、温度/功耗模式、网络、后台负载、客户端位置            |
| 适用性   | 必测/扩展/范围外清单、接口能力、传感器可用性、各缺项原因         |
| 统计设计 | 样本量、重复次数、种子、运行顺序、超时、失败与重跑政策           |
| 判定规则 | 主要指标、质量底线、延迟上限、等效容差、停止规则                 |
| 证据     | run_id、attempt_id、时间、原始记录路径、评分器及统计程序版本     |

预跑用于核验服务身份、计时、评分器与采集来源，另存诊断证据。正式样本量、扫描档位、持续时长与停止条件须预先冻结；少量预跑不能证明尾延迟或长期稳定性。能力子集明确题目 ID 与数量；评分真值仍需人工审核。

任何“稳定可用”“有效上下文”“达标”结论都依赖预注册质量、延迟和资源要求；未确定要求时仅发布观测结果及曲线。

## P2：计时与 token 口径

客户端全部时长用同一进程的单调时钟。记录：

- t0：客户端开始发送请求。
- t_content：首个非空生成内容到达，排除协议元数据与心跳。
- t_answer：首个可辨识的非空答案内容到达。
- t_last：最后一个内容块到达。
- t_end：完整响应正常结束。
- N_out：声明计数来源及覆盖范围的输出 token 数；只有引擎实际生成 ID/可靠内部计数才称实际生成量。端点 usage 是端点报告值，需核对定义；输出文本重新分词只能称估计，可能漏掉隐藏思考、特殊 token 和工具内容。

| 指标               | 计算与限制                                                                                                                          |
| ------------------ | ----------------------------------------------------------------------------------------------------------------------------------- |
| 端到端时间         | t_end - t0；包含本次请求的客户端/传输等待，客户端所在机器应注明。                                                                   |
| 首内容延迟         | t_content - t0；只有块事件时使用此名称，不声称已经取得服务端逐 token 计时。                                                           |
| 首答案延迟         | t_answer - t0；无法可靠区分推理通道与答案时标不可测。                                                                               |
| 引擎 decode 速度     | 引擎定义的生成 token 数 / 解码阶段时长；记录首 token 是否计入及版本定义。                                                               |
| 客户端输出间隔均速 | 只有真实逐 token 时间且 N_out 大于 1 时，可用 `(N_out-1)/(t_last-t_content)`；计数与事件须覆盖同一 token 序列；数据块接口不得套作逐 token 速度。 |
| 客户端完整有效吞吐 | N_out/(t_end-t0)，注明 token 来源；若用重分词数，称可见文本估计吞吐。另报同题完成时间，这不是纯 decode 速度。                           |
| prefill 速度        | 实际处理且未由前缀缓存复用的输入 token 数 / 引擎 prefill 时长；无阶段计时不能用 TTFT 代替。                                               |
| 排队时间           | 同一服务端时钟上的执行开始 - 入队；无调度事件即不可拆。                                                                             |
| 块间隔 / ITL       | 分块记录报告块间隔；真实 token 事件才报告 ITL。                                                                                        |

API 流式适配可参考[vLLM serve 指标实现](https://docs.vllm.ai/en/latest/api/vllm/benchmarks/serve/)，但需核实该端点是否把多个 token 聚在一个事件内。

token 计数统一记录：来源（引擎实际 / 端点报告 / 重分词估计）、tokenizer 版本、是否含模板/特殊 token、思考与工具字段，以及这些子项是否已包含在总数中。缓存命中输入和思考输出若是输入/输出的子集，不能再加一次。拿不到隐藏部分时保留未知。

跨模型有两条比较路径：相同内容/任务用于用户体验比较；各自 tokenizer 下相同 token 长度用于容量与计算压力比较，后者文本内容可能不同。两条路径分开标注。文中预跑的 1K/4K/8K 分别指 1024/4096/8192 token，正式记录仍用整数；字符数默认 Unicode 码点数，注明是否含空白、标点及模板，不等同汉字数或屏幕字形数。

接口首答案到达与屏幕首次显示是不同边界。若报告用户可见延迟，需要客户端渲染事件或带时间戳录屏；录屏精度受帧率和判读影响。非自回归生成没有等价阶段时，不强套 prefill/decode 速度。

跨机器不要直接相减各自单调时钟。用 request_id 关联本机阶段时间；需要计算跨机事件差时，记录时钟同步方法与误差。GPU 异步阶段测量需要引擎事件或同步，profiling 与同步开销单列。质量测试允许自然结束；性能强制定长如忽略 EOS 应单列，不能混入质量成绩。

## P3：状态、分母与统计

不能把适用性、运行成功、回答正确和传感器可读混成一个互斥字段。最少分四层记录：

| 层次       | 状态与规则                                                                                                                                         |
| ---------- | -------------------------------------------------------------------------------------------------------------------------------------------------- |
| 适用性     | 范围内支持、范围内不支持、范围外不适用；测试前固定，发现不支持时保留失败证据。                                                                     |
| 执行       | 活动契约使用 completed、failed、cancelled、invalid、not_executed 五终态；模型运行失败与工具/证据无效分开。固定时窗负载按冻结窗口及排空判断完整性。 |
| 质量       | 通过、未通过、无法评分或不适用；正常返回可以答错。质量测试因系统失败无答案，按任务规则计失败而不是自动排除。                                       |
| 测量完整性 | 各指标可测、不可测、缺记录；缺功耗传感器不使已完成的答案变成模型失败。                                                                             |

- 运行完成率 = 正常完成数 / 有效执行尝试数；质量成功率 = 验收通过数 / 应计入评分的有效尝试数。分母和排除项应公开；不得用运行完成率冒充质量成功率。
- 不支持而未执行的项目单独列兼容性状态；若属于必需能力，则判资格不合格或按固定基准计分，不从必需范围里删除以抬高总成绩。
- 测试基础设施损坏可判实验无效，但须预先定义归因，保留记录并将必要补测另存为新运行。取消由何方触发要注明；系统无法按时完成不能靠测试端取消改成非失败。
- 未测、无法评分和缺测逐项披露；不能计算完整官方成绩时仅发布子集结果，不声称全部验收通过。
- 延迟分布可报告完成请求的条件分布，但应并列失败率和超时预算。不能以删掉慢请求的方式改善 P95；超时属于截尾观测。
- 不支持是兼容性结果；若某任务在规定被测范围内要求此能力，能力得分如何处理按固定基准规则，不能临时改“不适用”逃避失败。
- 区间需先声明估计对象：固定完整题集的本次分数是描述值，重复运行区间描述随机性，按题抽样的区间依赖题目代表性；不能自动外推所有真实任务。
- 题目成绩按题目或题族聚类；同题多次采样不是多个独立题。性能串行采样有相关性时按运行块统计。
- 差异报告配对差值与 95%区间。预注册实用等效边界：只有差值区间落入等效范围才可支持实用等效；“没显著差异”不等于等效。
- 不必对所有分布硬套 bootstrap；全成功/全失败时朴素 bootstrap 会退化，可用适合独立二项样本的区间并说明假设，聚类数据另处理。
- 分位数显示样本量与算法；样本量不足或区间过宽时标探索性，不输出确定排名。不得看到有利结果就停止采样。
- 独立 k 次至少一次成功与 k 次全成功分别报告，附 k 和总预算。继承上轮反馈的修复重试是另一协议，不冒称独立 pass@k；重复请求不等于新增独立题目。
- ECE 等分箱指标要预定分箱并报告每箱样本量；此处二元 Brier 分数是“答案正确概率”与 0/1 正确标签的平方误差平均值；多分类版本需要完整类别概率和另行定义。自报置信度并非天然概率。
- SLO 是事先约定的延迟/错误要求；goodput 只统计同时满足声明要求的请求/s。加入质量门槛时明确本项目定义，不冒称工具默认指标。

自动评分先用已知正确、错误和边界样本校验。模型裁判属于候选方法，当前 CLI 使用确定性评分；若在其他协议采用裁判，需固定模型、提示词和预算并人工校准，其耗时与费用不混入被测模型推理成绩。

## P4：资源与环境采集

MON 应探测设备级、进程级和引擎级可用数据，保存实际支持的层次，不要求所有平台都同时提供。平台支持不同，缺失值使用 null 并附原因，不填 0。

- 分开记录进程 RSS/物理占用、引擎已分配/保留内存、设备总占用和系统可用量。统一内存这些值可能重叠，不能直接相加。
- 采样可从 100–500ms 预跑起步；以传感器实际更新率为准。报告“采样观测峰值”，引擎峰值计数器有则另存，不能保证捕获瞬时峰值。
- GPU 预留池和缓存可能保持高位；检查可复用容量、清缓存和重启对照后才将持续增长标为疑似泄漏。
- 对照开关采集器的短测试，确认采集开销；profiler 用于诊断的结果单列。
- 负载发生器放在独立机器或确认其不是瓶颈；如与模型共享 CPU/内存，明确报告影响。
- 温度、频率下降只说明相关；硬件限制原因不可读时不自动断言热降频。
- OOM、异常输入、权限和网络测试使用隔离环境与合成数据；恢复设备后再做正常性能测试。

## P5：能耗、噪声和续航

能耗是功率在时间上的积分。使用同一覆盖范围、同步后的时间窗口：

`E_joule = Σ ((P_i + P_(i+1))/2) × (t_(i+1)-t_i)`

- 总能耗含空闲基线；如另报净能耗，使用同条件空闲功率乘窗口时长后扣除，并标估算与误差。不要静默用净值替代总值。
- J/成功任务 = 同一批次全部执行尝试能耗 / 成功任务数；分母为 0 标不可计算。
- 并发时共享整机功率无法直接归属单请求，报告批次能耗或明确的分摊估算。
- GPU 部件能耗与整机插座能耗分开，不相加。多机方案需注明计量是否包含全部主机和网络设备。
- 功率计记录型号、量程、精度、采样率、校准与缺段；短任务小于仪器分辨能力时批量重复后报告批次平均。
- 噪声用固定距离/方位的声级计测 A 计权等效声级，记录背景声；低于背景可区分能力时不给精确设备噪声结论。
- 电池实测记录健康、亮度、电源模式及起止电量；短窗口外推续航只标估算。

以上为本项目计量设计，不表示获得 MLPerf 正式认证。正式 MLPerf 测量规则见[官方功耗文档](https://docs.mlcommons.org/inference/power/)。

## P6：成本模型

成本项分清实测与假设，统一币种、价格日期、使用周期和税费边界。

- 周期 TCO = 分摊硬件折旧 + 周期电费 + 维护/软件等费用 + 明示计价的人工；另列实际现金支出。
- 硬件可按“购置价减残值”在声明寿命内分摊；共享设备注明分配比例，不能同时重复计入整机全价和同周期折旧。
- 电费 = 实测或按声明负载估算的 kWh × 电价，注明空闲时段是否包含。
- 每成功任务成本 = 同一周期/批次归属成本 / 对应成功任务数，所有失败和重试成本计入。
- 已有设备方案报告新增现金与机会/折旧成本两套视角。人的等待时间与实际操作时间分开。
- 回本只在存在明确替代方案和正净节省时计算；不能只凭更快就推算回本。
- 对价格、利用率、寿命和电费给低/中/高假设，观察推荐是否改变；这是工程成本测算，不是收益保证。

## P8：最小证据包与发布前检查

每个 run 至少保存：实验 manifest、适用性清单、环境快照、请求/题目 ID、attempt、实际配置、输入输出或受控存储引用、评分依据、原始指标、状态、时间与产物哈希。重复项可以引用同一次采集，无需重复运行，但应保持指标口径一致。

1. 数量检查：计划清单、执行清单、逐题结果、汇总分母能对上。
2. 重算检查：抽样从原始日志重算时间、分数和能耗，结果一致。
3. 复现检查：固定版本配置在匹配环境抽样重放；性能采用事前容差，不要求逐字逐毫秒相同。
4. 公开检查：标明实测/估算/外部来源、缺项、限制和日期；依据数据许可对原始题目及日志分层开放。
5. 修订检查：保留旧结果与修订理由，引用不静默失效。
6. 实验独立性：同一模型题目分数与不同设备上的性能是否复用应明确；未复验的设备/配置不能宣称质量完全相同。

## P9：负载、并发与吞吐窗口

| 协议问题           | 本项目要求                                                                                                                                                                     |
| ------------------ | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------ |
| 封闭负载与开放负载 | 封闭负载维持在途请求，完成后才补下一个；开放负载按事先计划到达，不随响应变慢而自动减少请求。两者分别报告。                           |
| 计划到达与实际发送 | 保存计划、实际发送时间及差值；客户端排队延迟单列，并可报告从计划到达到完成的总等待。若客户端发不出目标流量，该点是负载未达标，不能称服务端已承受该到达率。                     |
| 批次默认口径       | 固定请求清单，结束发送后等待完成或预定超时。吞吐分母为第一条正式请求发出到最后一条正式请求终结的完整墙钟时间；分子只取同批次已完成请求/已生成输出，失败及部分输出单列。        |
| 稳态窗口口径       | 另设预热后的固定计量窗口，以窗口内完成数计请求吞吐；保留窗口初末在途数和逐请求归属。无法把流式 token 准确归属窗口时，不报告该窗口 token 吞吐。不能用窗口外的完成数除以窗口内时长。 |
| 停止与排空         | 预注册停止发新请求、排空截止和取消规则；计划数、实发数、完成数、失败数与在途数可核对。期末尚未完成的请求不静默消失。                                                           |
| 可持续容量         | 需同时满足声明 SLO/质量/允许失败比例，实际到达负载达标且队列无持续增长；短时 goodput 高不能证明可持续。                                                                           |
| 重试与缓存         | 原始请求与重试分别记账；系统内部重试计入原任务时间和成本。共享前缀和跨轮缓存命中公开，不把缓存效果误称纯算力提升。                                                             |

以上是本项目的计量约定；采用外部工具原生窗口定义时应保存其版本和定义并单列，不强行把不同口径放入同一排名。候选工具的具体事件含义需用小样本日志核对后才能接入。

## 方法落地的边界

选择方法后核验题包审核、接口适配、测量来源与冻结配置。缺能力、传感器或标注时保留缺测原因；候选工具名称、示例参数和目录覆盖不构成验收证据。独立操作者复现是可选观察，人工题包审核仍为正式要求。
