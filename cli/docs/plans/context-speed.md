# 长上下文速度专项测评

本计划依据 2026-10-18 的需求调整：新增专项题库，CLI 负责采集与结构化输出，
Studio 完成操作与展示；专项只展示 Card、Context、Prompt length、Time、Prefill、Decode。
当前先交付规划和指定 Lody「挑刺者」的审核，不将规划认可写成产品已经实现。
当前进度统一记在 [backlog](../backlog.md)。源码基线为 `1f3e9fa`。

## 执行关口

严格按用户指定顺序推进，不并行越过关口：

1. 指定 Lody「挑刺者」对最终规划明确审核通过；此前只允许调查、规划修订与复审，
   不开始模拟 UI 或正式功能实现。
2. 审核通过后，在项目现有 `--debug-ui` 中完成可点击模拟界面，遵守现有
   [design system](../../../studio/docs/design-system.md)。复用页面构建器、主题、控件、
   导航和 `previewIntent` 分派，不另画独立原型或另建应用。
3. 向用户展示并实际驱动模拟界面，等待用户明确认可；修改意见回到同一模拟界面修订。
   挑刺者批准、自动测试通过或未收到回复均不代替用户认可。
4. 只有界面获认可后，才以该界面为基准实现题库、CLI 采集/输出和 Studio 正式闭环；
   实现完成后另外验收并交由指定挑刺者审核。

模拟阶段只改页面和窗口内存模拟、相应测试与文档，不新增真实 CLI 命令、题库采集或
服务 IO。fixture 和模拟实现限定 `ui_debug && !release`；不创建 `core.Service`、启动模型、
下载或持久化设置。模拟历史只在窗口内保留；跨重启恢复用独立 fixture 展示预期状态，
实际重启读回证据要等正式功能阶段验收。模拟数值与预算明确标注为示例，不是性能结果。

## 用户能完成的流程

在 Studio「新任务」选择「长上下文速度」，选模型、引擎和一个上下文档位，查看本次
5 次测量与最坏时间预算，开始任务。Studio 完成候选准备、启动、绑定、冻结计划、
排队执行与读取结果。结束后点击「查看结果」进入原生表格；关闭并重新打开 Studio
后，可从历史任务打开同一结果。取消、安全停止、失败和缺测也能留在历史里查看。

每次任务只选择一个档位：64K / 128K / 256K 分别为 65,536 / 131,072 / 262,144 token。
换档位使用「用此组合新开任务」；已有受管服务参数不符时，明确提供停止旧服务、再启动
新任务的操作，不自动重启服务。外部服务只能显式绑定，Studio 不接管其生命周期。

「只展示六列」限制结果指标，不删除运行状态、错误原因、取消按钮和必要的任务信息。
模型、引擎、题库版本与测量次数放在表格上方。专项页面不显示质量分、正确率、内存曲线、
综合分或 SVG；后台仍采集安全控制和证据验证需要的数据。

本次不移除其他题库已有的 CLI HTML 报告，也不改默认 `zh-core` + `zh-svg-pelican` 范围。
选择专项即明确选择单一专项题库，不和质量题库混成一个任务。

## 六列的固定含义

| 列 | 来源和单位 | 缺测与限制 |
| --- | --- | --- |
| Card | 本次绑定设备的型号、显存容量；容量原始单位 bytes | 多 GPU 不能取清单第一张冒充被测卡；统一内存明确标记共享，CPU 显示 CPU；未知保留原因 |
| Context | 冻结配置并经服务核验的 `conditions.context_size`，token | 配置值不符服务时阻断，不以模型宣称最大长度替代 |
| Prompt length (tokens) | 模板后实测 `actual_input_tokens`，包括模板和特殊 token | 不用字符数、目标档位或正文长度代替；五次计数不一致不得合成一行 |
| Time (s) | 同请求最终引擎 `prompt_ms / 1000` | 表头说明「输入处理耗时」；沿用当前定义中包含首采样的范围，不冒充 E2E 或客户端 TTFT |
| Prefill (tok/s) | 现有 L06：`prompt_n / (prompt_ms / 1000)` | 分子是实际未缓存处理输入；无有效阶段计时不回推 |
| Decode (tok/s) | 现有 L07：`max(0, predicted_n - 1) / (predicted_ms / 1000)` | 当前定义排除首 token，计数含 reasoning / 特殊 token；不使用可见文本或 SSE 块数 |

汇总行展示五次有效测量的中位数，单元格可展开范围和逐次值，仍使用同六列。
逐请求核验引擎 `prompt_n + cache_n` 与模板后 `actual_input_tokens` 一致；计数缺失或
不一致时该请求标明原因并排除完整专项汇总，不能把一次预检计数复制五次当作逐次验证。
只在同一冻结设备、模型、引擎定义、context、输入文本/模板、缓存和输出协议内汇总。
缺测用 `—` 和原因；不补零、不拿最好值、5 次不报 P95。
全部执行完成与全部指标可测是两个状态。少于 5 个有效样本时展示已有逐次值及
`有效 n/5`，不显示完整专项的汇总成绩，不补跑来替换失败。
不同模型、设备或配方可以并列查看，不在此功能增加赢家、加速比或通用强制可比开关。
证据结论遵循[血缘规则](../data-contract.md#证据血缘与比较结论)。

## 专项题库与运行协议

新增随包资源 `zh-context-speed`，`task_protocol=performance`；包含三个固定中文长文本
case，分别归属三个 context 档位。文本采用项目自有、许可明确的固定材料，避免大量
重复短句构成失真的唯一负载。原文、case ID、规则和版本入库并绑定内容哈希。
每个 case 的参考答案为空、质量不适用；固定输出目标为 256 token。

样本文本按参考 tokenizer 选择接近截图工作量的长度，准备记录写清参考模型与实测数。
实际运行始终使用被测模型的模板/tokenizer；不同模型得到不同 Prompt length 是合法结果。
预算检查满足 `实际输入 + 256 <= 配置 context` 才发送；不适配时保留阻断原因，
不能临场截断或换文本。这个方案无需扩大 `prepare-length` 的 65,536 字符搜索上限。

专项配方固定并版本化：并发/槽位 1、请求顺序固定、5 个完整 trial、每 trial 1 次短文本
预热、输出 `strict_fixed_length=256`、空 stop、关闭 prompt cache 与投机解码。
采样配方固定 `temperature=0`、`top_p=1`、`top_k=1`、`min_p=0`、
`presence_penalty=0`、`repeat_penalty=1`、`seed=0`、`reasoning_mode=off`；
`seed_support=supported` 仍须按现有协议核验，不能仅凭声明视为已支持。
复用现有 fixed-output probe、cache protocol 和引擎构建验证；probe/预热与正式样本分开。
原始缓存计数必须证明正式样本未复用前缀；无法证明时标为指标缺测，不能按冷缓存成绩汇总。
保留既有 `max_requests` 正式请求计数口径；总墙钟预算包含 probe/预热和排空开销，
UI 区分「5 次正式测量」和额外准备请求，不把额外请求藏在预算外。
超时、总时限、可用内存、磁盘、温度及取消条件在发送前冻结并在 UI 可见。

最初可执行范围为已有计时定义验证的 Prism 适配器；KVMem/NInfer 和未知构建在 UI
给出具体不支持原因，CLI 同样拒绝该专项协议。后续引擎单独适配，不给它们套 Prism 公式。
软件实现覆盖现有 macOS/Windows 候选准备和对应队列；CLI Linux 可使用人工准备的合法
绑定配置。真机覆盖逐平台报告，不把本机或模拟结果推广到所有显卡。

题库新增内容仍走既有人工内容审核。规划审核与 Agent 自审不伪造人工批准；实施阶段
先准备完整文本、hash 与审核材料，再按仓库已有规则完成正式题库准入。`--diagnostic`
只用于明确标记的诊断验证，不作为正式成绩验收。社区资源变更的 owner 同轮重生成
`resources.json` 并执行 `export_community.py --check`。

## CLI 与 Studio 的边界

选择「复用标准证据执行、增加专项投影」方案。另一个方案是在 Studio 中直接调用
模型接口和计时，被排除：它会复制身份、token、取消、封存及度量规则，产生两份事实来源。
也不选择先生成完整 HTML 再让 Studio 取 index，因为那不满足本次专项输出要求。
候选比较由主会话完成，指定挑刺者独立审查；不称为多方案独立开发竞赛。

建议公共接口如下；这些是拟新增接口，不是当前可运行命令：

1. `init --bundle zh-context-speed --out NEW_DIR` 导出专项材料。Studio 在现有工作区下
   创建唯一的专项操作子目录；不重新 init 现有目录，不改普通题库选择或全局设置。
2. `config create ... --profile context-speed --context-size 65536` 生成专项候选。context
   可选三档；CLI 同时设置/核验 startup args、generation、cache 与预算，Studio 不改 TOML。
   模型最大 context 与资源可用性要实证核验，不允许 UI 任意放宽停止阈值。
3. `plan --preset context-speed --config BOUND_CONFIG --out NEW_PLAN` 选择该 context 对应
   case 并冻结五次试验。与既有 `--experiment` 互斥，调用同一计划校验和冻结实现。
4. `run --plan NEW_PLAN/plan.json --output-root NEW_BATCH` 复用正式执行路径；CLI 不启动、
   停止或重启引擎。Studio 只管理自己显式启动的进程，并保留真实绑定核验。
5. `speed-results --batch BATCH_DIR` 离线核验原始证据并向 stdout 返回结构化结果。
   不生成 HTML、Markdown、报告目录或新的结果缓存；Studio 历史打开时调用同一入口。

专项只通过 `speed-results` 输出六列及必要证据/状态元数据，不能通过通用报告或导出
间接生成 HTML 或另一套指标展示。以下均为实施时必须落实的准入规则，不能只隐藏按钮：

| 入口 | 专项来源处理 |
| --- | --- |
| `report --runs ...` | 读取来源并核验身份后、创建输出目录前拒绝 |
| `compare --left ... --right ...`（含 `side-by-side`） | 任一来源为专项即整次拒绝，不生成 `report.html` |
| `export --run ...` / `export --analysis ...` | 追溯原始 run；专项来源整次拒绝，不生成通用 JSON/CSV/Markdown 导出 |
| `rescore` / `repeat-summary` | 专项不产生通用质量重评或重复一致性派生物；创建目录前拒绝 |
| `public package` / `public plan` | 专项暂不进入普通社区成绩与重复计划协议；创建目录前拒绝 |
| `engine-fit compare` / `engine-fit verify --rerender` | 保持独立 `engine_fit_run.*` / `engine_fit_plan.*` 定义准入；标准专项 run 不得通过，添加拒绝样例 |
| `verify --rerender` | 专项或专项派生来源在任何写入前拒绝重新渲染；不得删除、重建或覆盖原始文件 |
| `verify`（不带 `--rerender`）/ `progress` / `speed-results` | 保留离线核验、进度读取和专项 JSON 投影，不产生通用报告 |

所有支持多来源的入口对普通与专项混合输入整次拒绝；来源标识缺失、损坏或血缘不符
按既有坏证据规则拒绝，不能落回普通报告。识别依据是核验后的 plan/profile、题库与
case 身份及来源链；各消费者复用同一判定，不能仅靠目录名或显示名称。
普通来源维持原有行为。新增可消费 run/analysis 的展示入口须加入同一专项准入检查。

使用独立结果类型 `context_speed_result.v1`，保留 `schema_version=3` 的活动 run 证据。
冻结计划增加可选的专项 profile 标识，既有无标识计划照常读取；专项标识、题库、case、
配置及协议必须交叉校验，不根据可编辑的 bundle 显示名授予资格。新字段源定义与
合法/非法样例、Schema 导出同轮更新；若实施发现必须改变旧字段语义，先重开本方案审核。

结果载荷包含批次/plan/run 身份与 hash、profile 版本、执行状态、测量完整性、每次
六列原始值及缺测原因、可选汇总行、停止原因和已完成/失败/取消/未执行计数。
单位固定为 bytes、token、s、token/s；只在 Studio 格式化显示。
每个速度值可追到同一 request 的分子、分母与计时定义；源文件损坏或血缘不符时退出 4，
不能从旧 UI 缓存显示为成功。未完成但可核验的批次返回部分结果，执行不完整退出 3；
指标缺失单独标记，不改写已经完成的请求状态。旧 run 缺少专项协议不补造专项成绩。

Studio 在 `core.Service` 增加固定专项计划入队和结果读取，沿用单 worker 的排他准入、
事件、取消、Shutdown、结果根包含和去重规则；不新建第二套执行队列。
批次路径和子 run 列表有明确类型，不能将 batch 路径塞进只接受单 run 的字段。
页面任务结果按普通报告/专项结果分派，计算在 CLI，Studio 只解析、校验和展示。

入口从「新任务」和「模型页→用此组合新开任务」汇合。新老工作区都可选专项；旧 CLI
不支持专项结果 schema 时，入口提示升级，普通任务可继续使用。
阶段为准备→启动与绑定→冻结计划→测量→读取结果→完成/部分/失败。
取消保留已产生的证据和原因，排空完成前不回到可启动状态；失败后的「重新测评」创建
新计划、新 batch，不覆盖旧结果、不自动 resume 或替换失败样本。
CLI `resume --from-run` 对专项子 run 同样在创建续测目录或发送请求前拒绝；已有 batch
不允许续跑后拼成五次完整成绩。重新测评必须新建完整计划与 batch，部分结果保持原样。
读取结果失败可单独重试读取，不再次执行模型。历史记录只引用本任务的源 batch，
不混入工作区其他模型、普通题包或旧运行。
历史扫描从 batch 的冻结计划及子 run inputs 中封存的计划/profile 识别专项并交叉核对归属，
不依赖 `report.html`。未完成 batch 可打开已核验的部分结果；无可核验样本时显示状态与
原因；损坏或读取失败保留任务及重读入口，不显示旧缓存成绩。

## 实施顺序与所有权

首个阻塞前置是规划审核，随后是用户对模拟界面的认可。正式功能中题库/协议和结果类型
先于 CLI 与 Studio 接入；接口及黄金样例冻结后才可分工，不同时派多个写者修改共享契约。
共享可变状态是 Git 工作树、题库清单、Schema、运行队列和 UI 预览模型。
最小安全分解如下，下一单元只依赖已验收的前置，不提前写后续阶段代码。

| 单元 | 主要范围 | 结束条件 |
| --- | --- | --- |
| P：规划审核 | 本计划、索引与 backlog | 指定挑刺者对最终冻结规划返回明确通过 |
| U：现有 UI 模拟 | 现有页面构建器、`--debug-ui` 内存模拟、测试与文档 | 正常、取消、缺测、失败/重读、历史查看可由按钮连续完成；原生窗口演示；用户明确认可 |
| A：协议与题库 | CLI 题库、profile、计划及结果契约、黄金样例 | 固定三档文本/配方；正常、缺测、部分、非法来源样例成立；人工审核材料齐备 |
| B：CLI 链路 | config/plan、既有计时归约、专项结果、无 HTML 分派 | 假引擎经公开 CLI 跑完五次并离线重算六列；中断、预算拒绝、坏证据正确处理 |
| C：Studio 闭环 | inferyard parser、core 入队/历史、页面结果类型与六列表 | 页面按钮完成正常/取消/失败/重新测评/重开历史，无 HTML 调用和产物 |
| D：一致性与验收 | 已认可模拟与正式实现的 parity、原生 UI E2E、文档 | 两条路径各自对照明确预期；原生窗口按钮闭环；明确真机覆盖 |

U 阶段保留正常功能已有的 parity 回归；专项尚无正式编排时只报告模拟交互和隔离检查，
不声称两条路径一致。C/D 阶段再将已认可的界面行为和独立预期接入正式编排对照。

## 必需验收

- CLI 手算：缓存 20、处理 80、prefill 400ms、生成 11、decode 500ms，应得到 Time 0.4s、
  L06 200、L07 20；该样本可验证公式，但因缓存不为零不能成为冷缓存专项汇总成绩。
- 拒绝/缺测：计时缺失、零时长、NaN、布尔计数、重复 JSON key、未知构建、投机字段、
  错误 case/profile、实际输入超预算、容量不足、提前 EOS、输出未达 256、取消/超时。
- 端到端边界：真实 CLI + 假引擎，三档分别覆盖，验证 schema、封存、按 request 重算、
  五次样本归属、旧结果不变、工作区和结果根路径边界。读取结果不产生模型请求。
- Studio：从 UI 选择专项和档位，显示预算，启动/绑定/运行/打开结果；取消活动项和等待项；
  启动或绑定失败后人工重试；结果读取失败后只重读；新建与重启 Studio 后打开历史；
  旧 CLI 降级；普通双题库任务仍生成自己的报告。
- 以命令 transcript 和产物目录证明专项流程从未调用通用报告、没有 `.html`；同时直接调用
  上表各拒绝入口，覆盖专项、混合、派生来源和坏血缘，断言拒绝且未创建任何输出目录，
  `--rerender` 拒绝前后原始文件哈希不变；允许的只读入口仍能返回结果。
  普通来源控制组仍可输出。`resume` 拒绝且不发送请求；不能只断言「HTML 按钮不可见」。
  正常/模拟 parity 覆盖结果类型、六列数值/缺测、状态和任务归属；
  用隔离的错误值或已复现分歧证明检查会失败，随后恢复。
- 原生 macOS UI 使用现有 `mise run test:studio-ui`，由按钮驱动而非场景切换完成流程；
  普通构建及 `ui_debug,release` 拒绝调试入口。Windows/Linux 真窗口未跑则明确未验证。
- 真实模型测量在已确认设备、资源预算和停止条件下单独执行；至少一个可运行档位取得
  真实阶段计数。不能把假引擎五次通过写成 64K/128K/256K 或全部显卡的性能验收。
- 同步 CLI surface/data contract、所属 subsystem、Studio README/design system、资源目录
  和 backlog；检查 Schema/catalogue/resources 生成物。只改文档的规划阶段只查链接与 diff。

UI 入口；在最终固定 diff 上交由指定 Lody 挑刺者审核。规划批准不替代实现审核和真实验证。
