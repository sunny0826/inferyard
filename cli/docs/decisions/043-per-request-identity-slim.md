# ADR 043：逐次身份复查不再扫描模型地址空间

状态：Accepted

## 背景

每个请求前，以及同一条周期守卫，都会调用 `verify_process`。
Linux 上这次调用会读完整的 `/proc/<pid>/maps`，用来看开跑时绑定的模型 inode 是否仍被映射。
没映射到时，已经改用启动参数里的模型路径做设备号与 inode 核对。
macOS 的模型绑定已经是这条路径核对。Windows 的模型绑定也已经是启动参数里的文件身份。

模板和运行库在预检时做内容哈希。逐次守卫对它们只做 `unchanged()` 的文件身份核对，不逐次重读内容。

## 决策

每次守卫仍核对 PID、进程启动时刻、可执行文件身份、启动参数、监听，以及已声明的 `slots_debug`。
模型绑定只保留启动参数中的模型路径：该路径应存在，且设备号与 inode 与开跑时绑定的模型文件相同。
Linux 不再为这个核对读取 `maps`。

macOS 仍保留一次 `lsof` 视图，因为可执行文件映射、监听和 Metal 绑定还用它。本决定不把模型检查改成地址空间扫描，也不删这张视图。
Windows 仍保留 CUDA 后端已加载库的核对。本决定不把模型检查改成 `memory_maps` 扫描。

不新增模板或运行库的逐次内容重读。预检时的内容哈希和逐次 `unchanged()` 保持现状。

新运行的模型绑定记为启动参数文件身份，不再记 `mapped_inode`。
旧证据按原字节读取，不改写。

## 后果

不再证明模型文件此刻映射在进程地址空间里。
启动参数里的路径仍指向开跑时的那个 inode，检查就通过。
进程已经卸掉原文件、路径却没变时，原来的回退路径也会通过；这条不是新放开的口。

`maps` 读失败不再使整次身份检查失败。
路径上的目录项已经换成新 inode、旧 inode 仍映射在进程里时，原来算通过，改完后拒绝。

不改资产哈希、dirty、空闲、排空、温停、内存停和评分分母。
